## 1. Tree（知识树）

```text
Day 16：Disaster Recovery，DR（灾难恢复）
│
├─ ① 先确定业务要求
│  ├─ RTO = Recovery Time Objective（恢复时间目标）
│  │  ├─ 多久恢复营业：最多能接受停机多久？
│  │  └─ 包含故障发现、资源恢复、配置、流量切换与业务验证等耗时
│  ├─ RPO = Recovery Point Objective（恢复点目标）
│  │  ├─ 账本最多缺多久：最多能接受丢失多长时间的数据？
│  │  └─ 看故障时刻与可恢复的最近有效数据时间之间的差距
│  └─ 目标是要求，演练结果是实际表现；不能把两者混成一件事
│
├─ ② 选择备用系统的准备程度
│  ├─ Backup and Restore（备份与恢复）
│  │  ├─ 平时保存备份、代码与部署配置
│  │  └─ 故障后恢复数据、创建或启动所需资源
│  ├─ Pilot Light（核心资源常驻）
│  │  ├─ 数据库复制等核心部分持续运行
│  │  └─ 应用尚未完整运行，接班时还需启动或部署
│  ├─ Warm Standby（小规模完整系统待命）
│  │  ├─ 已有能工作的完整小系统
│  │  └─ 接班时按需要扩容并切换流量
│  └─ Multi-site Active/Active（多站点同时运行）
│     ├─ 多个区域平时都处理正式业务
│     └─ 需处理数据一致性、写入冲突和故障后剩余区域的容量
│
├─ ③ 分清故障范围与数据问题
│  ├─ Multi-AZ（多可用区部署）：减少单个可用区故障影响
│  ├─ Multi-Region（多区域部署）：应对区域级故障等需求
│  ├─ Replication（复制）：保持副本同步，但错误也可能被同步
│  └─ Backup / PITR（备份／时间点恢复）
│     ├─ 找回误删除、错误修改之前的历史数据
│     └─ 恢复后仍须考虑恢复点之后的正常订单，不能直接全量覆盖
│
├─ ④ AWS Backup（AWS 备份服务）集中安排备份
│  ├─ Backup Plan（备份计划）：安排备份时间、保留期限等
│  ├─ Resource Assignment（资源分配）：明确资源或按标签选择
│  ├─ Backup Vault（备份保管库）：管理保存的恢复点
│  ├─ 按资源与区域支持情况配置跨区域复制，满足异地恢复需求
│  └─ 每日备份不自动满足分钟级 RPO；有备份也不等于已验证能恢复
│
├─ ⑤ Failover（故障转移）：让备用系统接班
│  ├─ Route 53（域名系统服务）：让后续 DNS 查询获得健康入口
│  ├─ Global Accelerator（全球加速器）：通过固定入口 IP 引向健康端点
│  ├─ ALB（应用负载均衡器）：把到达入口的请求分给健康后端
│  ├─ Auto Scaling（自动扩缩容）：按配置增加或减少应用实例
│  └─ 切换入口不会自动完成数据库提升、扩容、配置与权限修复
│
├─ ⑥ DNS TTL = Time To Live（域名解析缓存有效期）
│  ├─ 缓存有效期间，解析器可能继续返回旧入口
│  ├─ 新 TTL 不会追溯修改已缓存结果的原有效期
│  └─ 降低 TTL 不会加快数据库恢复，也不会主动迁移已有连接
│
├─ ⑦ Failback（回切）：原区域修好后按计划迁回
│  ├─ 接班期间的新订单也要同步回原区域
│  ├─ 协调主库身份、写入、应用配置和流量，避免两边各自写入
│  └─ 不必一修好就切回；可继续由接班区域服务，等待合适窗口
│
└─ ⑧ Disaster Recovery Drill（灾难恢复演练）
   ├─ 能否真正登录、下单和读取数据？
   ├─ 实际恢复耗时是否满足 RTO？实际数据缺口是否满足 RPO？
   ├─ 并行步骤取最长耗时，再加后续依赖步骤
   └─ 先排除不满足要求的方案，再比较成本、运维与复杂度
```

准备越充分，通常持续成本越高、恢复越快；但策略名称不是恢复时间承诺。最贵方案也不能自动解决误删除或所有数据丢失问题，实际效果要演练验证。

## 2. 四种策略：看备用区域平时在做什么

| 策略 | 备用区域的状态 | 简单类比 |
| --- | --- | --- |
| Backup and Restore | 主要准备备份及重建材料 | 保存账本和装修图纸，出事后重新开店 |
| Pilot Light | 核心资源在运行，应用尚需启动或部署 | 仓库和账本就绪，但还没安排收银员营业 |
| Warm Standby | 完整小系统已能工作 | 小店已经能营业，接班时增加人手 |
| Multi-site Active/Active | 两地平时都处理业务 | 两家店平时都营业，故障时健康门店接手流量 |

重点：**数据库副本运行，不代表整个备用应用已能工作。核心在运行 → Pilot Light；完整小系统已能工作 → Warm Standby；两地平时都营业 → Active/Active。**

## 3. RTO / RPO：目标与实际结果分开记

假设 14:00 故障，业务要求 RTO ≤ 45 分钟、RPO ≤ 10 分钟；14:35 恢复业务，可恢复数据截至 13:52：

```text
13:52               14:00                         14:35
最近可恢复数据         故障发生                        恢复业务
  └─ 数据缺口 8 分钟 ──┘  └── 恢复耗时 35 分钟 ────────┘
```

- 实际恢复 35 分钟 ≤ RTO 目标 45 分钟：达标。
- 实际数据缺口 8 分钟 ≤ RPO 目标 10 分钟：达标。
- 数据缺口从故障发生时刻往前看，不从恢复完成时刻往前看。
- 昨晚备份可以很快恢复，但不代表能接受丢失今天的数据；数据复制很及时，也不代表应用恢复足够快。

### 错题重点：并行步骤不能全部相加

```text
14:00 ── 数据库恢复 25 分钟 ──→ 14:25
      └─ 应用启动 15 分钟 → 14:15
                                  ↓ 等两者都完成
                           配置和验证 10 分钟
                                  ↓ 14:35
                             流量切换 5 分钟
                                  ↓ 14:40
```

整体耗时 = **max(25, 15) + 10 + 5 = 40 分钟**，不是 55 分钟，也不是 25 分钟。实际项目需按依赖关系、故障发现及各步骤耗时计算，不能只统计数据库启动时间。上述数字均为教学假设。

## 4. 接班流程：把旧知识串起来

```text
正常：用户 → 东京 ALB → 东京 EC2 → 东京数据库
                                  │
                                  └─ 复制数据 → 新加坡数据库

东京故障后：
恢复／提升备用数据库，准备应用并按需扩容
    ↓
检查网络、权限、密码和应用配置，验证业务
    ↓
按设计切换入口
    ↓
用户 → 新加坡 ALB → 新加坡 EC2 → 新加坡数据库
```

Route 53 或 Global Accelerator 帮忙指路，备用区域仍必须有能工作的应用与数据。部分恢复步骤可以并行，但有依赖的步骤不能跳过。

| 检查内容 | 对应旧知识 |
| --- | --- |
| 应用连的是否为新加坡数据库 | 应用配置、Parameter Store（参数存储） |
| 路由和端口是否允许连接 | VPC（虚拟私有云）、Security Group（安全组） |
| 应用是否拥有访问资源的权限 | IAM Role（身份角色）、Permissions Policy（权限策略） |
| 是否能取得正确数据库密码 | Secrets Manager（秘密管理服务）及凭证读取与刷新 |
| 是否能读取加密发票 | s3:GetObject + 对实际密钥有效的 kms:Decrypt 授权 |
| 是否具备足够处理能力 | ALB + Auto Scaling，及数据库等依赖容量 |

例：S3 发票已经放到备用区域，但应用缺少对应 KMS 密钥的解密授权，仍可能收到 AccessDenied（访问被拒绝）。有文件、有服务器，不等于能正常营业。

## 5. DNS TTL：改小新值不会修改旧缓存

教学假设：解析器严格遵守 TTL，不提前刷新、不使用过期缓存。

```text
14:00 解析器缓存东京入口，TTL = 600 秒 → 原到期时间 14:10
14:02 东京故障
14:03 权威端已返回新加坡入口，同时把 TTL 改为 30 秒
       └─ 旧缓存仍可有效至 14:10，不会因此改成 14:03:30 到期
14:10 旧缓存到期，重新查询才获得当时的答案和 TTL
```

- Route 53 无法直接清除所有外部解析器已有的缓存。
- 计划内切换可提前降低 TTL，并等待原 TTL 窗口过去；这不保证所有实际客户端行为完全一致。
- DNS 更新不主动中断已有连接，也不阻止仍到旧端的请求写入数据库。

## 6. 复制、历史恢复与回切的边界

### 误操作：副本可能一起出错

```text
10:00 错误改坏部分订单 → 错误复制到另一区域
10:00～10:20 仍有正常新订单
    ↓
保留现有数据和可用变更证据
    ↓
PITR 恢复出 09:59 的独立数据库
    ↓
核对、纠正错误，协调补入之后的正常订单与其他有效变更
    ↓
验证后按计划切换
```

复制不会自动辨认业务错误。直接用当前副本全量覆盖恢复库，可能把错误带回来；直接用旧恢复库接班，则可能遗漏新订单。具体合并与修复流程取决于业务和数据库能力。

### 单主写入场景的回切

```text
新加坡接班期间继续生成新订单
    ↓
修复东京，安排新加坡 → 东京的数据同步
    ↓
在允许的切换窗口暂停并排空旧端写入
    ↓
确认最终数据追平，协调主库身份与应用配置
    ↓
切换入口，防止旧端继续写入
    ↓
验证后恢复写入
```

这里只示意允许短暂停写、数据库不会自动协调主库的场景。不能仅靠 DNS 切换防止两端写入；健康检查通过也不证明数据已同步完成。也可以暂不回切，继续让新加坡承担主系统职责。
